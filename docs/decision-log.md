# Decision Log

## 项目名称
AI World Engine — AI 小说世界观推演系统

## 技术选型

| 层面 | 选择 | 理由 |
|------|------|------|
| 后端框架 | FastAPI | 高性能异步 Python Web 框架，OpenAPI 自动文档 |
| 数据库 | SQLite | 零配置，适合单用户本地使用，后续可迁移到 PostgreSQL |
| 模板引擎 | Jinja2 | FastAPI 官方推荐，轻量级 |
| 前端 | 原生 HTML/CSS/JS | 第一版不引入前端框架，保持简单 |
| AI 调用 | OpenAI-compatible API | 通用接口，支持 mock 模式 |
| 测试 | pytest | Python 生态标准测试框架 |
| Python 版本 | 3.10+ | 稳定版本，广泛支持 |

## 架构决策

### 1. 为什么第一版不用前端框架？
- 降低复杂度，减少依赖
- 本项目核心是世界观推演逻辑，不是前端交互
- 后续可以逐步迁移到 Flutter App

### 2. 为什么使用 SQLite？
- 零配置，无需安装数据库服务
- 单用户场景足够
- 后续可以通过 SQLAlchemy 迁移到 PostgreSQL

### 3. 为什么 AI 模块独立为 services？
- 解耦路由和业务逻辑
- 支持 mock 和真实 API 两种模式
- 方便后续替换 AI 提供商

### 4. 为什么推演结果不能直接写入正史？
- 防止 AI 幻觉污染世界观
- 用户必须审核后才能采纳
- 支持分支记录，保留多种可能性

### 5. 为什么使用 Jinja2 模板？
- FastAPI 内置支持
- 服务端渲染，无需额外构建步骤
- 适合内容型应用

## 风险分析

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| AI API 不可用 | 核心功能无法使用 | 提供 mock AI 模式 |
| AI 生成内容质量低 | 用户体验差 | 提供采纳/废弃机制 |
| SQLite 并发限制 | 多用户场景性能差 | 第一版单用户，后续迁移 |
| 前端简陋 | 用户体验一般 | 后续版本优化 |
| 安全漏洞 | 数据泄露 | 安全审查阶段专项处理 |

## 暂不实现功能
- 多用户系统
- 实时协作
- 本地 AI 模型集成
- 导出/导入世界设定
- 可视化时间线图表
- 移动端 App
